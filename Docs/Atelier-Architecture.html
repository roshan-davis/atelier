Architecture reference

Atelier Architecture

How Atelier is built today: the Swift targets, the catalog, the Develop render path and its threads, the on-device models, the outside tools and the MCP server for chat apps. It describes what the code on main does, read from the source, and marks where that differs from the PRD.

Atelier is one native macOS process (SwiftUI with AppKit where SwiftUI is too slow) over a SQLite catalog. Develop renders with Core Image on the GPU from the original file, decoded once per open photo and kept in a session; Grid and Loupe show cached JPEG previews. Edits are a JSON document per photo. Outside tools (Edit In apps, ComfyUI) run in their own processes; small selection, face, depth and denoise models run inside the app through Vision, Core ML and ONNX Runtime (CPU at this revision). Chat apps reach the app through a small stdio helper that relays to a private Unix socket.

The two big source areas are AtelierApp (35.8k lines: views and controllers, with DevelopController.swift alone at 3,720) and AtelierCore (27.3k lines, of which Develop is 18.2k).

3Runtime layers

At run time the app is a main-actor view layer, a set of main-actor controllers that own state, and Core services that do the work on background queues. Storage is the catalog package plus a few files in Application Support and Caches; everything else is another process or a file on a drive.

4App shell and state

  • Launch. AtelierApp is a SwiftUI App with one WindowGroup("Atelier") and a Settings scene. CatalogLaunch opens the catalog on the splash screen and builds LibraryModel; if the catalog can't open, it offers to try again rather than starting empty. AppDelegate turns off window tabbing, takes a catalog snapshot on quit and asks about unsaved HDR changes.
  • One hub. LibraryModel (1,240 lines plus extensions for actions, HDR, Lens Blur, notes, import, private photos) owns the catalog, preview cache and scheduler, DevelopController, HDRController, AIController, AgentServer, the action registry, EditWatcher and the shared ZoomState. Modes are a ViewMode enum: grid, loupe, develop, hdr; Lens Blur is a sub-mode of Develop (develop.isLensBlurring).
  • Library rows are live queries. observeRows() and observeSidebar() are two separate GRDB ValueObservations, iterated in main-actor Tasks. Each tracks the database region its query reads: a commit that touches that region re-runs it, a write elsewhere doesn't, and GRDB may fold several commits into one publication. A changed filter cancels and restarts the rows observation.
  • State that outlives a mode (zoom, pan, focused photo) lives on LibraryModel / ZoomState, which every photo view reads and writes. SessionRestore saves view, sidebar item, filter, photo, zoom and grid scroll as a SavedSession in UserDefaults.
  • Preferences are UserDefaults (about 50 keys, read directly in 169 places). Develop, Tone Curve and Color Grading presets, import presets and export presets are JSON files in ~/Library/Application Support/Atelier, shared across catalogs.
  • Shared UI pieces named in AGENTS.md: ZoomViewport, Cursors, ClickGestures, DeleteFeedback, PanelSection, SliderRow/DevelopSlider/SliderGeometry, GroupHeading, PhotoPicker, one PhotoMenu, KeyBindings and the action registry. Tests (ClickGestureTests, AtelierActionsTests) fail on some bypasses.

5Catalog and data model

Catalog is a final class marked Sendable around a GRDB DatabasePool (WAL, foreign keys on). Features add tables through extensions (Catalog+Cull, +Stacks, +VirtualCopies, +Pairs, +Private, +Notes, +Processors), each registering its own migration; the Develop tables come from v3-develop in Develop/Catalog+Develop.swift and the processor tables from v8-processor-documents in Processors/Catalog+Processors.swift. Reads and writes are synchronous calls on writer.read/writer.write, made from whichever thread the caller is on.

  • Package layout: ~/Pictures/Atelier/Atelier Catalog.atelier/ holds catalog.sqlite, Previews/ and Backups/. snapshot(keep:) runs GRDB's online backup on quit and keeps the newest N (Settings default 10).
  • Develop settings are one DevelopSettings struct (schema 3), stored sparsely: a [Parameter: Double] map plus typed fields for crop, curves, masks, Lens Blur areas, spots, profile and Upright. Anything at its default is left out, so equal looks compare equal and old JSON decodes with neutral defaults.
  • History (DevelopHistory) is a list of named steps with full settings and snapshots, serialized next to the settings.
  • Volumes are matched by volume UUID (VolumeIdentity); mount and unmount notifications refresh online state.
  • Private photos: import entries and collections carry a private flag; LibraryFilter.privacy hides them from the library queries (rows, sidebar, counts) until Touch ID or the password (LAContext in PrivatePhotos). Agent tools check visibility separately and treat a private photo as missing, whatever the view shows.

6Import

ImportFlow in the app drives progress (ImportStatus: files, bytes, speed, time left). Metadata comes from ImageIO (MetadataReader, ShootingInfo); XMP sidecars found on import restore Develop settings, history and notes (DevelopRecovery, HistoryRecovery, NotesRecovery).

7Previews and thumbnails

On disk

  • PreviewCache: two sizes, 256 px and 2560 px JPEG, sharded by id & 0xff. Thumbnails use the embedded RAW preview when it is large enough.
  • PreviewCache.version (now 12) is written to version.txt; an older folder is moved aside at launch and deleted in the background.
  • PreviewScheduler: two OperationQueue lanes (thumbnails with max(2, active cores / 2) workers, previews with 2), de-duplicated by asset and size, cancellable, with a failed set that is retried only when something changes. Edited photos render through Develop settings.

In memory

  • ThumbnailLoader (grid): an NSCache of decoded thumbnails, decoded off the main thread.
  • PreviewImages (Loupe, Develop open): an LRU of 8 decoded 2560 px previews (the code's comment estimates about 18 MB each at 2560 × 1707; the real size depends on aspect ratio and decoded format), keyed by asset and file date, decoded in a detached task so the first draw doesn't decode on the main thread.
  • The import sheet has its own NSCache of file thumbnails.

8Develop render pipeline

Develop renders start from the original file, decoded once when the photo opens and kept in a session, so a slider tick doesn't decode it again. DevelopRenderer.shared owns one CIContext (linear Rec. 2020 working space, half-float, cacheIntermediates: false). A DevelopSession holds one opened file: the CIRAWFilter (or decoded image) and caches for that photo. session.image(with:) builds the Core Image graph under the session's lock.

  • Mask sources come from the sharp photo after the Remove spots and before Lens Blur, on the uncropped frame; each mask is then put through the same crop as the photo. Luminance ranges are worked out later, from the photo the mask sees. Fine Edges mattes are shared app-wide through FineMatteCache; Select Sky is derived from the depth model's output, not a model of its own.
  • Option-drag views branch off or return early: Defringe's views show step 1 alone, Visualize Depth replaces the photo, and the clipping and sharpening views replace the result at the end.
  • Panel switches are applied first (applyingPanelSwitches()), so a panel that is off is absent from the graph. Tools at their neutral value return the input unchanged.
  • Per-pixel work in the live path is Core Image filters or runtime Metal kernels (RuntimeKernels.build). Small CPU tables (curve LUTs, the color cube) are built in Swift.
  • Warm-up: PipelineWarmUp.warmUpVariants renders every tool once off screen, so the first drag of a tool doesn't compile its kernel on the photo.
  • Lens Blur is gated by session.rendersLensBlur; Develop, previews, export and Loupe leave it out, and the result reaches the library as a stacked TIFF (LensBlurPhoto).
  • Full size: when an edit rests, a second, full-resolution session renders on atelier.develop.full so zoomed views are sharp; the proxy is 2560 px long edge.

9Develop threading and display

The goal of this path (AT-025, AT-036, AT-039) is that a slider drag never waits on the main thread or SwiftUI. The render queue presents its own frames.

  • Where the direct path applies. When the photo view is attached to the live feed and a frame fits it, the render queue sets the layer's contents itself after epoch, count and size checks. Otherwise (no surface free, an incompatible frame, a view without the live feed, the crop tool, the mask overlay, Option-drag views) the render comes back as a CGImage and the main thread shows it. The main thread still handles input and builds each request.
  • Settle and save are separate. 0.12 s after the last frame the image is published to SwiftUI and the history step settles. Writing to the catalog is its own 400 ms debounce (saveTask, then flushSave on the main thread).
  • Latest wins. LatestJob keeps at most one waiting request; a newer one replaces it. The render queue drains itself, so a busy main thread cannot hold the GPU idle. Measuring has its own LatestJob so the histogram never builds a backlog.
  • Generations and epochs. Requests carry openGeneration and a live epoch; frames for a photo you have left, or for another view key, are dropped and their surfaces returned to the pool.
  • Opening photos. Decodes run on a concurrent atelier.develop.open queue and start only after ← → rest for 0.15 s. Neighbours in the Filmstrip are decoded on atelier.develop.prefetch (utility) after 0.8 s without a render. The cached 2560 px preview shows first.
  • Other Develop queues: .full (full-size render when idle), .navigator (560 px preset hover previews), .warm-up, .previews (stored preview refresh), .timing-log.
  • SwiftUI isolation. DevelopController has 87 @Published properties, so per-tick values are kept out of it: the histogram and color scope live on DevelopMeasures, slider values flow through equatable rows, and Frame Diagnostics (DevelopFrameHUD) reads timings from the render queue.

10Masks and on-device models

12Agents and MCP

  • One command path. Each AtelierAction is declared once with a kind and Swift parameter types; JSON schemas are generated from the types; Docs/agent-actions-catalog.json is regenerated by Scripts/agent_catalog.py and a test fails when it is stale.
  • Changes: every agent write names its targets (ids, selection or current). Library and Develop edits that are recorded get a change id and an Undo notice; a change above Settings > Agents' photo limit (50) asks first. command_batch runs up to 50 of the supported write steps; atomic makes those all or nothing. Private photos read as missing.
  • Threads: the socket server accepts on a Thread and serves each connection on its own Thread. Some Look reads run off the main thread; other tools hop to the main actor because their handlers use LibraryModel. A Develop call made during a drag waits for the drag to end and is refused, with a retry message, if waiting fails.
  • MCP Apps: ui://atelier/photos is a carousel view for clients that declare the UI extension; its thumbnails come from a view-only get_thumbnails tool.

13Cull, Match Look, Export, XMP

Cull

CullModel runs per session, on files before import or on cataloged photos. Culling builds CullSignals per photo (Vision feature print, Laplacian sharpness on 1024 px, faces with eye openness, subject sharpness, layout grid), groups similar shots and picks with CullPick (Pick By modes). Groups and reasons are saved in cullGroup tables and notes.

Match Look

LookMatcher (Core, with Tone, Skin, Regions and Emulator extensions) fits Develop settings so a photo matches a reference or one of the built-in SVG studies; MatchLookModel in the app runs fits on atelier.matchlook.fit and previews on .preview. Fitting is CPU Swift on small copies.

Export

Exporter opens a non-interactive DevelopSession per photo at the export size, renders in the chosen color space and writes JPEG, HEIC, TIFF or PNG with metadata and an optional watermark. Export presets are JSON in Application Support.

XMP

ImageIO reads standard metadata on import (MetadataReader). Atelier's own XMPSidecar reads and writes sidecars: standard fields plus three custom packets (atelier:DevelopRecovery, HistoryRecovery, Notes) on demand or automatically (Settings > Metadata, xmpDirty flag). They are read back on import to recover edits. Exiv2 is not used.

15Tests and tooling

  • Test targets: AtelierCoreTests (the bulk: render math, catalog, import, masks, models, Lens Blur), AtelierHDRCoreTests, AtelierAppTests (registry, click gestures, Develop modes, histogram sink), AgentActionsTests, AgentMCPTests, AtelierActionsTests, plus Tests/AtelierUITests (native smoke suite). Some tests need sample RAWs and skip without them.
  • Checks: Scripts/check_pr.py (whitespace, help index, build, tests; logs in .build/local-checks/), Scripts/check_ui.py and LayoutSnapshots.swift (screenshots off screen), compare_snapshots.swift.
  • Builds: Scripts/build_macos_app.py --arch arm64|x86_64|universal|all makes an ad-hoc-signed Atelier.app with the helper inside.
  • Help: HTML pages in Sources/AtelierApp/Help, index from Scripts/help/build_help_index.py, before/after pictures from make_help_images.py.
  • CI: .github/workflows/build.yml (macOS 15 runner: build, tests with sample NEFs, UI smoke). Operational note, not something the source shows: runs have often failed without starting because of GitHub billing, so Mac-local checks are the main gate.
